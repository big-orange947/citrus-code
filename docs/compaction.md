# 上下文压缩

## 窗口与策略

窗口由模型配置的 `context_window` 声明，默认 1,000,000 tokens；不自动查询服务端容量。
切换模型后重新建立压缩控制器，使用新模型窗口。下面列出默认 1M 模型的预算；
较小窗口的阈值与摘要预算相应缩小。

| 参数 | 当前值 |
| --- | --- |
| 上下文窗口 | 配置值，默认 1,000,000 tokens |
| 自动压缩触发线 | 窗口的 60%，默认 600,000 tokens，包含等于 |
| 近期保留目标 | 最近 5 轮完整模型交互 |
| 近期交互软预算 | 约窗口的 10%，最多 100,000 tokens |
| 每次摘要请求的新增历史预算 | 窗口的 40%，最多估计 100,000 tokens |
| 单次摘要最大输出 | 窗口的 10%、8,192、模型声明上限三者的较小值 |

一轮是一次模型回答及其全部工具结果。没有工具调用的完整回答也算一轮。保留时从最新一轮向前选择，最多 5 轮；加入更早一轮会超过软预算时停止。至少保留最新一轮完整交互，因此单轮特别大时允许超过软预算。

软预算针对近期模型回答和工具结果，系统提示和单独保留的用户要求另计。原文预算、摘要预算和最终完整请求的 token 数不是同一个数字。

## 触发位置与执行顺序

```text
接纳用户消息或排队消息，并保存
 → 本轮开始
 → before_model 更新当前请求的系统提示
 → 估算完整请求
 → 不到窗口的 60%：直接调用任务模型
 → 达到窗口的 60%：选择保留项，生成摘要
 → 检查摘要非空、正常结束、压缩后低于阈值
 → 发出 context_compacted 事件
 → CodingSession 保存 compaction 记录
 → CLI 显示压缩前后大小
 → 继续本轮模型调用
```

工具批次执行期间不压缩；收齐结果后，在下一次模型调用前检查。单批结果可能使上下文暂时超过 60%，但不会为了严格卡住阈值而截断正在执行的批次。

压缩不结束任务，也不额外消耗主循环的模型轮数预算；摘要请求本身仍消耗模型服务额度。摘要过程可以由 Ctrl+C 取消。

## token 计数

优先使用最近一条有效助手消息的 usage，计算其输入与输出总量，加上随后新增消息的大小估算。usage 为零、缺失、模型不匹配、错误或中断的响应不作为基线。缓存命中量不重复加到已经包含它的输入总量上。

原始系统提示仍保存在历史中，CLI 恢复后可能换用更长的当前提示。计数会为这部分正向差值额外留出空间。这是保守近似：已经取得新提示对应的 usage 后，该差值仍可能多计。

压缩前保留的助手消息，其 usage 描述的是旧的大请求。压缩后忽略这些旧 usage，直到出现压缩记录之后的新助手响应。

没有有效 usage 时，估算整份实际请求，包括当前系统提示、工具定义和消息。英文等 ASCII 文字按约 4 字符一个 token，非 ASCII 文字采用更大的估算系数；图片采用固定占位预算，不把 base64 当文字计算。这不是模型的精确 tokenizer，阈值是针对估算值的规则，实际服务用量可能不同。

## 保留项与切分规则

保留以下内容：

1. 原始系统消息；实际请求仍采用本次启动的系统提示。
2. 当前任务的用户原话，以及当前任务期间已接纳的 steering 消息。
3. 最近最多 5 轮完整交互，受近期交互软预算限制；默认 1M 窗口对应 100,000 tokens。

`CodingSession.prompt()` 新建的用户消息标记 `taskStart=true`。接纳 follow-up 消息时开始下一项任务；steering 消息属于正在执行的任务。当前任务的用户消息会跨越多次压缩继续保留。下一次空闲状态的 prompt 会开始新任务；之前的目标和约束可以进入历史摘要。

保留原有消息的先后顺序，同一消息只保留一次。较早版本的会话没有任务起点标记时，以最近的真实用户消息作为回退；CLI 接收下一次任务后会写入明确的任务起点。

```text
assistant：调用 read(id=a)、grep(id=b)
tool：a 的结果
tool：b 的结果
```

上面三条属于同一组，必须整组保留或整组总结。缺少结果、没有对应调用、名称不匹配等情况不能通过压缩掩盖；需要先恢复或修复会话。

## 摘要内容与输入限制

摘要通过当前 Provider 直接请求，不运行另一个 Agent，不提供工具。摘要使用以下结构：

- 目标。
- 约束与偏好。
- 已完成与进行中。
- 关键决定。
- 错误与未知状态。
- 下一步。
- 重要文件与符号。

再次压缩时，把上一份摘要和这次被移出的消息合并。工具调用只是尝试，不自动代表文件已经修改成功；提示要求摘要保留成功、失败、未验证和状态未知的区别。

历史序列化为文本，明确作为待总结数据。每条工具结果最多选取约 2,000 个字符，保留头尾并标记中间省略；工具参数文本超过 12,000 字符时截断。图片仅保留附件说明。原始完整消息仍在会话文件中。

过大的历史拆成若干文本片段，按预算分批生成摘要，每批合并前一份摘要。单条特别长的消息也会分段，避免摘要请求本身溢出。摘要响应必须正常 stop；空摘要、length、错误、异常工具调用或异常大的摘要均不采用。

## 持久化和恢复

原始树节点保留，新增一种 `compaction` 节点，保存：

- `summary`：摘要正文。
- `retainedEntryIds`：本次仍保留原文的消息节点 ID，按原顺序排列。
- `tokensBefore`、`tokensAfter`：压缩前后估计大小。
- 通用节点的 `id`、`parentId`、`timestamp`。

`build_context()` 按当前分支依次应用压缩记录，得到“系统消息 + 最新摘要 + 保留原文 + 后续消息”。摘要被映射成一条明确标记为历史背景的用户角色消息，不提升成系统指令。

`get_branch()` 和 `get_entries()` 仍可读取原始节点；`get_context_entries()` 返回当前模型上下文及其来源 ID。`/history` 展示当前压缩后的对话，`/tree` 包含原始节点和压缩节点。切换到压缩前的分支位置，可以重建该位置的原始上下文；达到阈值时仍会重新压缩。

存储层在追加和加载压缩记录时检查引用顺序、重复引用、来源是否可见，以及工具调用与结果是否完整。旧摘要必须合并，不能同时作为原文再次保留。

摘要生成阶段不写文件。只有接收到 `context_compacted` 事件时，`CodingSession` 才同步提交压缩记录；写入完成后，事件才交给 CLI，然后模型循环继续。这样取消与摘要完成同时发生时，不会出现只写了记录却没有切换运行时上下文的中间步骤。

## 失败边界

- 摘要失败或被取消：不写压缩记录，保留原上下文，本次任务以 error 或 aborted 收尾。
- 必须保留的用户要求和近期交互自身已达到阈值：报错，不强行删除它们。
- 已无可总结的较早交互，或摘要没有使请求降到阈值以下：报错，避免无效重复压缩。
- 压缩记录写入失败：CLI 按存储错误退出，需要重新加载检查；沿用已有的单写入者和 JSONL 错误处理规则。
- 当前没有额外实现上下文溢出后的自动重试。单次输入特别大、估算误差或工具定义特别大时，仍可能遭遇服务端限制。

摘要会丢失细节。重要代码仍应按路径重新读取，临时日志可能被系统清理。压缩不是文件回滚，也不能恢复工具进程。

## 源码职责

| 文件 | 职责 |
| --- | --- |
| `coding/compaction/tokens.py` | 默认预算和大小估算 |
| `coding/compaction/controller.py` | 阈值判断、近期轮次选择、任务要求保留、准备压缩记录 |
| `coding/compaction/summarize.py` | 文本序列化、分段摘要和取消处理 |
| `coding/session/projection.py` | 根据原始记录重建压缩后的上下文 |
| `agent/context.py` | 通用的模型前上下文准备接口 |
| `coding/coding_session.py` | 按事件提交压缩记录，保持运行时与存储一致 |

`CodingSession` 默认启用压缩。自定义 `before_model` 若要改写普通对话消息，可以传入 `auto_compact=False`，自行管理上下文；当前自动压缩只允许 Hook 修改系统消息和工具定义。直接使用 `Agent` 不会自动启用 coding 层策略。

本次实现只进行了语法与静态检查，没有运行自动化测试或真实模型压缩验证。`FakeProvider` 只输出预设文字，不能验证摘要质量。
