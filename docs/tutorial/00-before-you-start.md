# 第零章：开始开发 Agent 前，你需要知道什么

[教程目录](README.md) · [下一章：第一次模型调用](01-first-call.md)

假设用户在终端输入：

> 读取这个项目，找到登录失败的原因，修改代码并验证。

一个 coding agent 怎样把这句话变成文件读取、代码修改和测试执行？这一章围绕这个任务，
介绍后续会用到的名词，并串起一次完整的运行过程。

阅读时先抓住三件事：模型根据什么作出判断，程序怎样执行动作，执行结果怎样影响下一次判断。
Python 语法与具体库的用法，会在后面首次使用时解释。

## 0.1 我们最终要做出什么

在这个任务中，Agent 可能经历下面的过程。这里是教学示意，实际采取哪些动作取决于项目和模型返回的内容。

| 阶段 | 模型提出的下一步 | 程序实际执行 | 得到的反馈 |
| --- | --- | --- | --- |
| 了解项目 | 查看项目说明和目录 | 读取文件、列出目录 | 项目结构和运行方式 |
| 定位问题 | 搜索登录相关代码 | 搜索并读取匹配文件 | 登录函数、调用位置和相关测试 |
| 确认现象 | 运行有关测试 | 执行测试命令 | 失败信息与退出码 |
| 修改代码 | 修正发现的问题 | 按指定内容修改文件 | 修改成功或失败的结果 |
| 验证结果 | 再运行有关测试 | 执行测试命令 | 测试是否通过 |
| 答复用户 | 说明修改与验证情况 | 在终端显示回答 | 用户看到最终说明 |

模型服务接收到的是程序提交的信息。项目文件要先由工具读出，再把相应内容交给模型；
修改和命令执行也由程序提供的工具完成。

我们的目标是实现支撑这条链路的程序：接入模型，提供 coding 工具，维护消息和运行状态，
保存会话，并在 CLI（命令行界面）中接收输入、展示进度。

## 0.2 大模型、Agent、工作流分别是什么

### 大模型：根据输入生成输出

LLM 是 Large Language Model，通常译为大语言模型。这里先把模型调用理解成：
程序提交指令、对话和相关资料，模型生成回答，也可能生成工具调用请求。

例如，程序把登录函数和错误信息一起交给模型，模型可能回答“这里读取了错误的配置项”，
也可能请求继续查看配置加载代码。模型生成的判断是否正确，需要结合实际代码和验证结果判断。

### Agent：根据反馈连续推进任务的系统

本教程把 Agent 理解为：以模型判断为驱动，通过程序执行工具，并根据反馈继续推进任务的系统。

一次普通问答可以在模型回答后结束。登录修复任务则可能需要多次读取、执行和修改；
程序每次把新结果交回模型，模型再决定下一步。这个持续交互的过程是我们要实现的核心。

### 工作流：程序预先安排执行路径

Workflow 通常译为工作流。比如程序预先安排：

```text
读取指定文件 → 请求模型给出修改 → 应用修改 → 运行指定测试
```

执行顺序和分支主要由程序设计。工作流可以在某个节点调用模型，也可以包含 Agent；
Agent 内部同样可以使用固定流程。理解一个系统时，可以观察“下一步由谁决定”，
不用先把整个产品归入某个互斥类别。

### 运行时与 Harness：让模型持续工作的程序

Runtime 是运行时。在本项目中，它维护消息与状态、请求模型、调度工具，并处理结束与取消。
例如模型请求读取文件后，运行时找到对应工具，把结果追加到消息列表，再安排下一次模型调用。

Harness 的用法在不同项目中略有区别。本教程用它指围绕模型组织任务执行的整套程序与机制，
包括运行时、工具、上下文准备、执行环境，以及相关控制逻辑。
运行时是其中负责驱动执行的部分，CLI 则负责人与程序之间的交互。

## 0.3 程序怎样与模型通信

模型服务通过 API（应用程序接口）接收程序请求。远程服务通常使用 HTTP 传输数据，
请求和响应中常用 JSON 表示结构化内容。

| 名词 | 在本教程中的含义 | 具体例子 |
| --- | --- | --- |
| 供应商 | 提供模型调用服务的一方 | 模型官方服务或中转服务 |
| 模型 ID | 服务用于选择模型的标识 | 在配置中填写的 `model` 值 |
| 接口地址 | 请求发送的位置 | 某个服务的 `/chat/completions` 端点 |
| API Key | 服务验证调用者身份的凭证 | 放在认证请求头中的密钥 |
| 请求头 | HTTP 请求的附加信息 | 认证方式、内容类型 |
| 请求体 | 本次提交的业务数据 | 模型 ID、消息列表、生成参数 |
| 协议 | 通信双方约定的数据结构和交互规则 | 消息字段、工具调用格式、流式事件格式 |

“OpenAI 兼容接口”通常表示服务支持相应 OpenAI 接口的数据格式。
需要进一步确认它兼容的是 Chat Completions、Responses 等哪一种接口，以及支持哪些参数。
兼容协议不决定底层模型的身份，也不保证所有可选功能都相同。

代码里的 Provider 还会指“供应商适配器”：一个负责把内部数据转换成具体服务协议、
再把响应转换回内部格式的组件。后文提到“注册 Provider”或“调用 Provider”，通常说的是这个组件。

```text
Agent 的统一消息
  → Provider 转成服务要求的请求
  → 模型服务返回响应
  → Provider 转成统一消息和事件
  → Agent 继续处理
```

比如切换到另一种协议后，工具调用的字段可能发生变化。由 Provider 处理这种差异，
主循环就可以继续按“取得助手回复、执行其中的工具调用”来工作。
第一章会展示一份完整的 HTTP 请求，后续再把这部分封装成统一模型层。

## 0.4 消息、提示词与上下文

### 消息是对话的基本记录

一条普通文字消息可以写成：

```json
{
  "role": "user",
  "content": "找到登录失败的原因，修改代码并验证。"
}
```

`role` 表示消息角色，`content` 表示内容。下面用 Chat Completions 的角色名称说明概念；
其他协议和项目内部类型可能采用不同表示，后续由 Provider 转换。

| 角色 | 内容来源 | 在示例任务中可能放什么 |
| --- | --- | --- |
| `system` | 应用提供的行为指令 | 结合工具结果处理代码任务，说明实际验证情况 |
| `user` | 用户的问题和要求 | 排查并修复登录失败 |
| `assistant` | 模型的回复 | 请求读取登录代码，或给出最终说明 |
| `tool` | 程序执行工具后的结果 | 文件内容、测试输出或执行错误 |

一条助手回复可以同时包含文字和工具调用。工具结果还要关联对应调用，
这样模型才能知道“这段内容是哪次动作得到的反馈”。

### 提示词：程序给模型的指令与输入

Prompt 通常译为提示词。日常交流中，它可能指一段指令，也可能泛指一次提交给模型的输入。
为了表达清楚，本教程会具体区分系统指令、用户任务、项目约定、历史消息和工具说明。

例如 `AGENTS.md` 是项目里的约定文件。程序需要读取它，并把有关内容组装进模型请求，
模型才会在这次调用中接收到这些约定。文件放在磁盘上本身不会完成这一步。

### 上下文：模型这一次实际接收到的信息

Context 通常译为上下文，可以包含当前任务、历史消息、工具结果、项目约定、摘要与工具声明等。

```text
第一次调用：用户任务 + 项目约定 + 可用工具声明
第二次调用：上述内容 + 模型的读取请求 + 文件读取结果
第三次调用：有关历史 + 新的工具调用及结果
```

这里描述的是概念上的信息组成，实际请求格式由所用协议决定。
应用可以选择、裁剪和整理这些信息，不一定每次把完整会话原样发送。

### Token、上下文窗口与输出上限

Token 是模型处理内容时使用的计量单位。文本会被拆成 token，拆分方式取决于模型，
不能把一个 token 固定等同于一个汉字、一个英文单词或一个字符。

上下文窗口限制模型一次能够处理的信息规模，输出上限限制一次生成的规模。
服务可能还对输入、输出和思考内容的预算设置不同规则。开发时需要为当前输入和后续输出留出空间。

例如，上下文窗口很大，模型仍然可能因为本次输出预算不足而无法一次生成完整文件。
向工具提交的代码正文也是模型输出，会占用生成预算。

### 历史、状态、会话和记忆有什么关系

| 概念 | 关注什么 | 示例 |
| --- | --- | --- |
| 对话历史 | 已经发生过哪些消息交互 | 用户任务、助手调用、测试输出 |
| 运行状态 | 程序此刻处于什么情况 | 正在请求模型、正在执行命令、是否收到取消 |
| 会话 | 怎样组织持续对话与记录 | 保存消息、选择分支、恢复上下文 |
| 记忆 | 信息怎样跨步骤或跨任务再次使用 | 近期历史、历史摘要、按需读取的项目说明 |

这些应用层信息与模型训练得到的知识是不同来源。对于本教程的调用方式，
某条历史记录即使已经保存到磁盘，仍需要被程序选入当前请求，才会参与这次回答。
保存会话、组装上下文和调用模型是相互关联的三个动作。

## 0.5 模型怎样调用工具

登录代码在本地磁盘上。为使模型获得它，我们可以提供一个名为 `read` 的工具。
这条链路包含工具声明、模型提出调用、程序执行和结果反馈。

### 先声明能力，再接收具体调用

工具声明（Tool Definition）告诉模型：工具叫什么、用途是什么、参数应该具有什么结构。
下面是简化的教学表示，不对应某家接口的完整工具报文：

```json
{
  "name": "read",
  "description": "读取指定路径的文件内容。",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {"type": "string"}
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
```

其中 `parameters` 使用 JSON Schema 描述参数结构：参数整体是对象，`path` 必须存在，
值应为字符串，并且不接受额外字段。`type`、`properties`、`required` 等是规范中的关键字，
`path` 是这个工具自己定义的参数名。见 [JSON Schema 对象说明](https://json-schema.org/understanding-json-schema/reference/object)。

模型根据任务和这份声明，可能生成下面的工具调用（Tool Call，也常称 Function Calling）。
这同样是简化后的表示：

```json
{
  "id": "call_1",
  "name": "read",
  "arguments": {
    "path": "src/login.py"
  }
}
```

`arguments` 是这次调用实际使用的参数。Schema 描述“应该长什么样”，
arguments 表示“这次具体传什么”，两者用途不同。
有些协议在线上传输的 arguments 是 JSON 字符串，Provider 会解析成内部使用的对象。

### 程序校验并执行，模型接收反馈

收到调用后，程序检查工具是否存在、参数是否符合要求，再调用实际的 Python 实现。
例如，如果 `path` 缺失或变成数字，就需要按工具规则拒绝这次执行，并返回可解释的错误。

Schema 提供了结构描述，应用仍然需要落实执行前的校验。本教程后面会使用 Pydantic，
由同一份参数模型生成 Schema，并校验实际 arguments。
路径对应的文件是否存在等实际状态，还需要在工具执行时检查。

```text
模型请求 read，参数为 src/login.py
  → 程序查找 read 工具
  → 校验参数
  → Python 读取文件
  → 形成关联 call_1 的工具结果
  → 将助手的调用和工具结果放回上下文
  → 再次请求模型
```

工具结果（Tool Result）可以包含文件文字、命令输出、结构化信息或错误。
结果中的调用 ID 用来与助手提出的调用配对，避免多次工具调用的结果混淆。

例如，这次读取成功后的结果可以简化表示为：

```json
{
  "tool_call_id": "call_1",
  "content": "这里是 src/login.py 的文件内容……"
}
```

下一次请求要携带有关的助手调用和这条结果，模型才知道自己请求读取的文件返回了什么。

模型生成“我先读取文件”这句话，只是文字输出；只有程序收到并处理可识别的工具调用，
才会进入实际执行。一个工具也可以被连续调用多次，每次使用不同参数并返回各自的结果。

文件读取、写入、编辑、搜索与 Shell 命令，都是 coding agent 常见的工具能力。
本章先理解它们如何接入循环，具体参数与实现会在工具章节中介绍。

## 0.6 Agent 主循环到底怎样运行

### 根据新反馈继续决定下一步

ReAct 来自 Reasoning 与 Acting，核心思路是让推理和动作交替进行，
通过环境反馈更新后续判断。其出处是 [ReAct 论文](https://arxiv.org/abs/2210.03629)。
本教程参考这一思路，用结构化工具调用与结果反馈组织任务执行。

```text
用户提出任务
  → 程序组装上下文，请求模型
  → 接收并检查完整响应
  → 响应请求调用工具？
      是：校验并执行工具，追加调用和结果 → 再次请求模型
      否：响应正常结束，且没有待续接输入 → 结束本次运行
```

这张图描述的是正常路径。网络错误、生成截断或用户取消，还需要专门处理。
“没有收到工具调用”本身不能说明成功，例如连接在响应完成前断开，也可能没收到完整调用。

回到登录任务，可以把一次运行展开成下面的轨迹。表中的判断是为了讲解动作选择所作的概括，
不是要求模型必须逐句输出的内部推理记录。

| 轮次 | 这次模型获得的新信息 | 模型返回的动作或答复 | 程序随后做什么 |
| --- | --- | --- | --- |
| 1 | 用户任务、项目约定、工具声明 | 请求查看项目说明和目录 | 执行有关工具，把结果加入历史 |
| 2 | 项目结构和运行方式 | 请求搜索登录相关代码 | 执行搜索，加入匹配文件与位置 |
| 3 | 搜索结果中的路径与位置 | 请求读取相关代码和测试 | 执行读取，加入文件内容 |
| 4 | 登录代码与有关测试 | 请求运行有关测试 | 执行命令，记录失败输出和退出码 |
| 5 | 测试失败信息 | 请求修正某个配置项的读取 | 执行编辑，记录修改结果 |
| 6 | 编辑已完成的反馈 | 请求再次运行有关测试 | 执行命令，记录验证结果 |
| 7 | 测试结果 | 给出修改说明，没有工具调用 | 正常结束，展示最终答复 |

工具是否执行成功、测试是否通过，都以实际返回结果为依据。某次工具报错后，
程序可以把错误作为结果交给模型，模型再决定换路径、调整参数或说明阻碍。

### 一次调用、一轮与一次运行

不同项目对 Step、Turn 的命名并不完全一致。本教程采用下面的约定：

| 名称 | 本教程中的含义 |
| --- | --- |
| 一次模型调用 | 向模型提交上下文并接收这次响应 |
| 一轮 / Turn | 主循环中的一次模型调用，加上该响应触发的工具执行 |
| 一次运行 / Run | 接纳任务后，主循环连续工作直到正常结束、取消或失败 |
| 一步 / Step | 描述任务动作时使用的普通说法，需要注明是计划项、模型轮次还是工具调用 |

一轮可能没有工具，也可能有多个工具调用。一次用户任务往往需要多轮。
实际代码中的网络重试可能发出多次 HTTP 请求，但不因此增加主循环的业务轮数；
后续摘要等辅助调用，也要与主循环轮数区分。

### 程序怎样决定停止

本项目的主要结束情况如下：

| 情况 | 运行时的处理含义 |
| --- | --- |
| 正常响应结束，没有工具调用，也没有待续接输入 | 结束本次运行，等待新的用户输入 |
| 有有效工具调用 | 执行并反馈结果，继续下一轮 |
| 生成被长度限制截断 | 报告截断，不执行这次回复中的工具调用 |
| 用户取消 | 请求停止当前工作，并记录相应结束状态 |
| 错误无法恢复 | 结束并报告错误 |
| 达到显式配置的最大轮数 | 因预算边界停止；本项目的轮数上限可以不设置 |

“运行正常结束”描述的是控制流程，任务是否完成还要结合模型说明和验证结果判断。
没有自动测试的项目，也可能需要其他检查方式，或者明确告诉用户尚未完成哪些验证。

### 计划列表和主循环是什么关系

模型可以先提出“了解项目、定位问题、修改、验证”的计划。
界面要显示当前计划项，需要应用保存相应状态，再把它展示出来。
计划可能由文字解析或专门工具维护，具体方式由实现决定。

Plan and Execute 通常表示先组织计划，再执行计划中的任务，必要时调整计划。
它与 ReAct 的反馈循环可以组合：某个计划项内部仍可能需要多次工具交互。
单凭 UI 出现计划列表，无法判断系统底层采用了哪一种完整控制结构。

本教程先实现模型与工具的反馈循环，再逐步加入工程能力。它能走多远，取决于模型判断、
工具能力、可用上下文、执行可靠性与反馈质量，不只是循环本身写了多少行。

## 0.7 把循环变成可用程序，还需要什么

这一节先认识用途。后续章节会在具体问题出现时，实现对应机制。

### 流式输出、SSE 与事件

Streaming 是流式输出：服务逐段发送生成内容，程序可以边接收边展示，减少等待完整回答的空白时间。
这些片段可能是文字，也可能是尚未拼完的工具名称、参数等数据。

SSE 是 Server-Sent Events，是一种通过 HTTP 传输事件流的格式，使用 `text/event-stream` 内容类型。
模型服务可以用它承载自己的增量响应。见 [SSE 格式说明](https://html.spec.whatwg.org/multipage/server-sent-events.html)。
接收 SSE 只是网络读取的一环，还需要解析其中的服务数据，再转换成项目内部事件。

Event 是事件，表示“刚刚发生了什么”，例如文字新增、工具执行开始、工具执行结束、Agent 结束。
CLI 根据事件更新界面，保存会话的组件也可以根据相应事件记录已完成的消息。

```text
服务的流式数据
  → Provider 解析
  → 内部文字、调用、完成或错误事件
  → 运行时处理并发出任务和工具事件
  → CLI 更新文字、动画和执行状态
```

文字可以边接收边显示。工具执行需要更严格的边界：本项目会等本次响应完整接收、
工具参数成功解析并通过校验后，再进入执行阶段。
只收到一半的 JSON 参数，还不足以执行工具。

### Hooks：在既定位置加入逻辑

Hook 可以理解成程序预留的扩展点。运行时到达某个位置，会调用注册的逻辑。
本项目提供四个主要位置：

| 位置 | 可以加入什么 |
| --- | --- |
| 模型调用前 | 整理本次上下文、加入当前项目指令 |
| 模型调用后 | 观察响应、记录用量与诊断信息 |
| 工具执行前 | 检查调用，必要时阻止执行 |
| 工具执行后 | 处理返回结果，再交给后续流程 |

例如每次调用模型都需要附上当前项目约定，可以通过模型前 Hook 组装，
主循环继续负责调用与执行顺序。Hook 做什么、能否修改数据，由接口定义。

### 状态与会话：运行中维护，结束后恢复

工具调用 ID、历史消息、当前执行阶段、用户追加的要求，都需要保存在相应状态中。
Session 则组织持续对话与记录，使程序能恢复已有任务，或选择历史中的一个分支继续。

比如重新启动后，应用先加载已保存记录，重建当前分支的上下文，再请求模型继续。
会话保存了哪些记录、哪些操作已经写入磁盘，决定了实际可恢复的边界。
保存聊天记录本身不代表能恢复一个进程退出时正在执行的命令。

### 重试与取消：控制失败和停止

Retry 是重试。模型响应途中断开时，可以按策略等待，再请求这一轮模型响应。
需要区分失败的临时输出和已完成的历史，避免把残缺调用交给工具执行。
重试模型请求，也不意味着把之前已经执行成功的文件修改和命令再执行一次。

Cancellation 是取消。用户按下取消键后，程序需要向模型请求、工具执行和等待逻辑传递停止信号。
已经完成的文件修改仍然存在；取消后的记录应说明实际完成到哪里。

### 输出截断与上下文压缩：控制信息规模

工具一次返回整份巨大日志，会增加模型输入和处理负担。Truncation（截断）可以限制返回规模，
保留预览，并提供进一步查看的方式。它与模型因为输出预算不足而中断生成，是发生在不同位置的长度控制。

Compaction（上下文压缩）用于历史逐渐变长的情况：应用把较早内容整理成摘要，
保留最近必要的交互，重新组织下一次模型输入。
压缩需要保留工具调用与对应结果的完整关系，避免留下无法配对的消息。

工具截断控制某次结果，压缩整理整个上下文。二者都需要判断任务接下来还要用到什么信息。

### 执行环境与沙箱：工具到底在哪里运行

文件和命令工具需要一个实际执行环境，可以是本机，也可以是容器或其他隔离环境。
Sandbox 通常译为沙箱，用于限制执行程序可访问的文件、进程、网络等资源，具体边界取决于实现。

Citrus Code 当前默认在本机执行工具，采用可替换的执行接口，为后续接入其他环境留出位置。
工作目录用于确定相对路径等行为，它本身不构成文件访问隔离；系统提示中的约定也不能代替执行环境的限制。

## 0.8 pi 的设计思路，以及我们的项目分层

pi 将统一模型 API、Agent 运行时与 coding 应用组织成不同部分，见
[pi 项目说明](https://github.com/earendil-works/pi)。Citrus Code 参考其职责划分，
使用 Python 实现自己的接口与工程结构。

```text
CLI
  接收输入，展示模型和工具事件
    ↓
coding 应用层
  项目约定、会话、上下文管理，组装 coding 工具
    ↓
agent 运行时
  维护状态，驱动模型调用与工具反馈循环
    ├→ ai 模型层 → Provider → 模型服务
    └→ 工具运行器 → 文件、搜索、命令工具 → 执行环境
```

对应到仓库中的位置：

| 目录 | 主要职责 | 后续会解决的问题 |
| --- | --- | --- |
| `src/citrus_code/ai/` | 统一消息与事件，适配模型协议 | 换供应商时，如何保持上层调用方式一致？ |
| `src/citrus_code/agent/` | 状态、主循环、Hooks、工具调度 | 模型和工具怎样持续交互，何时停止？ |
| `src/citrus_code/coding/` | 项目上下文、会话、压缩与具体工具 | 一个 coding 应用需要哪些额外能力？ |
| `src/citrus_code/cli/` | 参数、终端输入与事件展示 | 用户怎样与运行中的 Agent 交互？ |

例如换一种模型协议，首先修改或增加 Provider；更换文件执行环境，需要调整工具执行操作；
修改工具卡片样式，则主要影响 CLI。分层的目的，是使这些变化能够在职责明确的位置处理。

本教程会逐步采用统一模型接口、简单反馈循环、事件展示与 Hooks 扩展，
再补齐会话、重试和压缩等能力。它是参考 pi 的学习实现，不要求与 pi 的 API、事件名称或功能完全一致。
